## 2. 项目概述

### 2.1 背景与目标
用户缺乏专业植物养护知识，容易因浇水过频、光照不足、施肥不当等原因导致植株死亡。本产品通过 **拍照识别植物 + RAG 知识库检索 + 用户历史打卡数据** 三重信息融合，生成**个性化、可追溯、防幻觉**的养护建议，帮助用户科学养植。

**核心目标：**
1. 建立每株植物的数字化档案与养护数据沉淀（植物记录 + 数据图表 + 日历打卡）。
2. 通过 AI-RAG 固定工作流输出「有知识库依据」的个性化养护建议。
3. 形成「识别 → 养护 → 记录 → 反馈 → 优化建议」的闭环。

### 2.2 产品定位
面向 C 端家庭园艺爱好者的**智能养植助手**：既是养护记录工具（工具属性），也是个性化养护顾问（AI 属性）。

### 2.3 目标用户与典型场景
| 用户画像 | 典型场景 |
|---|---|
| 新手养植者 | 买了绿萝不知道多久浇一次水 → 拍照识别 → 获取养护建议 → 打卡记录 |
| 进阶养植者 | 多盆植物需要差异化养护 → 按植物查看数据图表与异常告警 |
| 出差/健忘用户 | 依赖日历打卡与 AI 提醒，保持养护连续性 |

### 2.4 术语与缩写
| 术语 | 说明 |
|---|---|
| RAG | Retrieval-Augmented Generation，检索增强生成 |
| RAGFlow | 企业级知识库/向量检索服务（主检索引擎） |
| ChromaDB | 本地轻量向量库（用户侧个性化上下文 / 缓存检索） |
| LangChain | LLM 链式工作流编排框架 |
| 打卡 | 用户对某株植物的一次养护行为记录（浇水/施肥/修剪等） |
| 数据图表 | 基于打卡与传感器/手动录入指标生成的趋势图表 |
| Fallback | 降级输出：知识库无匹配时输出的通用养护知识（需标注） |

## 3. 总体架构

### 3.1 系统架构（逻辑视图）
```
┌──────────────────────────────────────────────────────────────┐
│                        前端 Vue 3 (Vite)                      │
│   登录注册 │ 植物记录 │ 数据图表 │ AI智能养护 │ 日历打卡       │
└───────────────┬──────────────────────────────┬───────────────┘
                │ HTTPS / REST(JSON)            │ 图片上传(Multipart)
                ▼                              ▼
┌──────────────────────────┐   ┌───────────────────────────────┐
│      FastAPI 后端网关     │   │  文件服务(本地/MinIO 预留)      │
│  JWT鉴权 · 数据隔离 · 校验  │◄─►│                              │
└───────┬──────────────────┘   └───────────────────────────────┘
        │
        ├─► 业务模块：auth / plants / metrics / checkins / user
        │
        ├─► AI 模块（LangChain 链式工作流）
        │    节点1 图像识别 → 节点2 植物名提取
        │    → 节点3 RAG检索(RAGFlow) → 节点4 打卡拼接
        │    → 节点5 LLM 个性化生成(防幻觉约束)
        │
        └─► 数据层：Tortoise-ORM → 数据库(MySQL/SQLite) · ChromaDB(向量缓存)
```
**设计理由：** 后端采用**单体分层 + 模块化路由**（Auth/Plants/Metrics/Checkins/AI 独立模块），契合 Vibe Coding 模块化开发与 Skill 质检；AI 链路独立为编排层，便于替换图像识别模型与检索源。

### 3.2 技术栈
| 层 | 选型 |
|---|---|
| 前端 | Vue 3 + Vite + Pinia + Vue Router + ECharts |
| 后端 | Python 3.13 + FastAPI + Uvicorn |
| AI 编排 | LangChain（链式工作流 / LCEL） |
| 知识检索 | RAGFlow（HTTP API，主检索）+ ChromaDB（本地向量缓存/个性化上下文） |
| ORM | Tortoise-ORM |
| 数据库 | MySQL 8（生产）/ SQLite（开发本地） |
| 鉴权 | JWT（access + refresh） |
| 图像识别 | 多模态 LLM 视觉接口（预留独立识别服务扩展点） |
| 虚拟环境 | Windows 下 `.venv` |

### 3.3 全局强制规范（来自 systemprompt，本文档全部需求遵守）
1. AI 模块 = LangChain 链式工作流 + RAGFlow 向量检索，优先检索知识库，再结合用户打卡记录生成个性化建议。
2. 所有模块开发完成后，必须适配内置 Skill：**代码自动质检、接口单元测试、权限校验测试**。
3. 全局 JWT 鉴权、用户数据隔离（任何跨用户数据访问一律 403）。
4. AI 固定工作流链路：图像识别 → 植物名称提取 → RAG 知识库相似文档检索 → 用户历史打卡记录拼接 → LLM 个性化生成（详见第 8 章）。
5. 代码单一职责、可复用、注释完整、无冗余；交付输出附带：代码路径、依赖、启动命令、单测用例。
6. 禁止幻觉：LLM 输出必须优先匹配 RAG 知识库内容；无匹配则输出通用标准养护知识并**标注**（`is_fallback=true` + 前端明示"通用知识"）。

### 3.4 统一接口返回格式
所有接口（含错误）返回统一结构：
```json
{
  "code": "200",        // 业务码，字符串。见 9.3 错误码表
  "msg": "success",     // 人类可读消息
  "data": { }           // 业务数据；无数据时为空对象 {}
}
```
- HTTP 状态码与业务码独立：HTTP 仅表达传输/网关层语义（200/401/500…），业务结果以 `code` 为准（便于网关与业务解耦）。
- `data` 必须为对象或数组的容器，禁止裸返回标量；分页场景按 9.5 分页结构封装。

## 5. 功能需求详情

> 每个页面统一结构：`5.x.1 页面说明 / 5.x.2 功能点与验收编号 / 5.x.3 业务逻辑 / 5.x.4 交互规则 / 5.x.5 异常场景`。
> 验收编号（FR-xxx）与第 11 章测试用例一一对应。

### 5.1 P1 登录注册

#### 5.1.1 页面说明
用户账号的注册、登录、退出与会话刷新入口。未登录访问任何业务页面时统一重定向至本页（路由守卫）。

#### 5.1.2 功能点（FR-1xx）
| 编号 | 功能点 | 优先级 |
|---|---|---|
| FR-101 | 用户名/邮箱 + 密码注册 | P0 |
| FR-102 | 账号密码登录 | P0 |
| FR-103 | 登录态保持与 Token 自动刷新 | P0 |
| FR-104 | 退出登录（注销 Token） | P1 |
| FR-105 | 用户资料查看与修改（昵称/头像/简介） | P1 |
| FR-106 | 修改密码 | P1 |
| FR-107 | 密码强度校验与输入校验 | P0 |

#### 5.1.3 业务逻辑
1. **注册**：`username`（3-20 位字母数字下划线）、`email` 合法格式、`password`（≥8 位，含字母与数字）；用户名/邮箱唯一（冲突返回 409）。注册成功即签发 Token 自动登录，并初始化默认个人设置。
2. **登录**：支持用户名或邮箱 + 密码；密码使用加盐哈希（bcrypt/argon2）比对，禁止明文传输与存储；连续失败 5 次锁定 15 分钟（防暴力破解）。
3. **会话**：签发 `access_token`（有效期 2h）与 `refresh_token`（有效期 7d）；access 过期后前端用 refresh 换取新 access；refresh 失效则强制重新登录。退出时服务端将该会话 refresh 加入黑名单。
4. **权限边界**：登录/注册/刷新 3 个接口为公开接口；其余全部要求 `Authorization: Bearer <token>`。

#### 5.1.4 交互规则
- 表单实时校验，错误内联提示；提交按钮 loading 态防重复提交。
- Token 过期返回 `code=401` 时，前端统一拦截 → 尝试刷新 → 刷新失败跳转登录页（**不弹未捕获错误**）。
- 头像上传复用 9.6 文件上传规范。

#### 5.1.5 异常场景
见 10.2.1：用户名已存在、验证码缺失（暂不引入验证码则跳过）、密码错误锁定、Token 过期/黑名单等。

### 5.2 P2 植物记录

#### 5.2.1 页面说明
用户植物档案管理主页：卡片/列表展示用户名下所有植物，支持增删改查、图片上传、快捷发起 AI 识别与打卡。

#### 5.2.2 功能点（FR-2xx）
| 编号 | 功能点 | 优先级 |
|---|---|---|
| FR-201 | 植物列表（分页 + 关键词/状态筛选） | P0 |
| FR-202 | 新增植物（名称、品种、图片、位置、种植日期、备注） | P0 |
| FR-203 | 植物详情（档案 + 指标摘要 + 最近打卡 + 快捷入口） | P0 |
| FR-204 | 编辑植物资料 | P1 |
| FR-205 | 删除植物（含其打卡/指标/AI 建议的级联处理） | P1 |
| FR-206 | 植物图片上传/更换 | P1 |
| FR-207 | 植物状态标签（健康/待关注/异常） | P1 |

#### 5.2.3 业务逻辑
1. **数据隔离**：所有查询强制 `WHERE user_id = 当前登录用户`；对他人植物的读写一律 403（见 7.3）。
2. **新增**：`species`（品种）可选；若用户上传图片，可选触发 `POST /ai/identify` 预识别植物品种并回填建议值（非强制）。
3. **状态标签**：由规则引擎生成——最近 7 天存在"异常指标"（见 5.3 阈值表）或连续 ≥3 天未打卡且到了建议浇水周期 → `异常`；部分指标越界 → `待关注`；否则 `健康`。状态为**派生字段**，不手动编辑。
4. **删除**：事务性级联删除该植物下 `care_records / plant_metrics / ai_advices / user_checkins`；删除二次确认。
5. **图片**：仅支持 jpg/png/webp，≤5MB；服务端校验类型与大小，落地后返回可访问 URL。

#### 5.2.4 交互规则
- 列表分页参数 `page/page_size`（默认 1/10，上限 50），筛选 `status`、`keyword`。
- 删除、状态变更等破坏性操作需二次确认弹窗。
- 图片上传进度条展示，失败可重试且不阻塞表单提交（图片 URL 可为空）。

#### 5.2.5 异常场景
见 10.2.2：资源不存在 404、非本人资源 403、图片格式/大小非法 400、删除中断导致脏数据（事务回滚）。

### 5.3 P3 数据图表

#### 5.3.1 页面说明
以图表可视化某株植物的养护数据：指标趋势（温/湿度、光照、土壤湿度、pH）、打卡分布、AI 建议时间线。数据源：手动录入指标 + 打卡记录。

#### 5.3.2 功能点（FR-3xx）
| 编号 | 功能点 | 优先级 |
|---|---|---|
| FR-301 | 指标录入（手动：温度/湿度/光照/土壤湿度/pH） | P0 |
| FR-302 | 指标趋势折线图（按天聚合，可选时间范围） | P0 |
| FR-303 | 打卡类型分布（饼图/柱状） | P1 |
| FR-304 | 指标异常高亮与告警提示 | P1 |
| FR-305 | 导出数据（CSV，可选） | P2 |

#### 5.3.3 业务逻辑
1. **录入校验**：温度 -20~60℃、空气湿度 0~100%、光照 0~200000 lux、土壤湿度 0~100%、pH 0~14；越界返回 400 并给出合法区间提示。
2. **聚合口径**：趋势图按自然日取当日多条记录的平均值；查询区间默认最近 30 天，支持 7/30/90 天切换。
3. **异常阈值（规则引擎，驱动 FR-207/FR-304）**：
   | 指标 | 正常区间 | 待关注 | 异常 |
   |---|---|---|---|
   | 温度 | 15~30℃ | 8~15 或 30~35 | <8 或 >35 |
   | 空气湿度 | 40~70% | 30~40 或 70~80 | <30 或 >80 |
   | 土壤湿度 | 30~60% | 20~30 或 60~75 | <20 或 >75 |
   | 光照 | 5000~50000 lux | 2000~5000 | <2000 |
   | pH | 5.5~7.0 | 5.0~5.5 或 7.0~7.5 | <5.0 或 >7.5 |
   说明：阈值为通用默认值，若该植物已获得 AI 建议中的品种级阈值，则优先使用品种阈值。
4. **数据权限**：仅能查询本人植物；指标记录仅支持新增与按天覆盖（同植物同日再次录入视为更新），不支持删除单条（审计需要）。

#### 5.3.4 交互规则
- 图表基于 ECharts 渲染，空数据显示占位"暂无数据，请先录入指标"。
- 录入提交走统一返回格式；录入成功后自动刷新当日聚合点。

#### 5.3.5 异常场景
见 10.2.3：越界录入、非法时间范围、空数据、他人植物 403。

### 5.4 P4 AI 智能养护（核心页面）

#### 5.4.1 页面说明
产品核心页：用户拍照/上传图片 → 系统走 **AI-RAG 固定工作流**（第 8 章）→ 返回植物识别结果 + 个性化养护建议（含知识来源、置信度、降级标注）。

#### 5.4.2 功能点（FR-4xx）
| 编号 | 功能点 | 优先级 |
|---|---|---|
| FR-401 | 植物图像识别（返回品种 + 置信度） | P0 |
| FR-402 | 生成个性化养护建议（触发完整 AI-RAG 链路） | P0 |
| FR-403 | 建议内容渲染（分节：浇水/光照/施肥/温湿/病虫害） | P0 |
| FR-404 | 建议来源展示（引用的知识库文档列表） | P0 |
| FR-405 | 降级标注（`is_fallback=true` 时明确提示"通用知识"） | P0 |
| FR-406 | 历史 AI 建议列表与详情 | P1 |
| FR-407 | 建议反馈（有用/无用），用于质量迭代 | P2 |
| FR-408 | 建议一键关联到植物档案（可选建档） | P1 |

#### 5.4.3 业务逻辑
1. **触发方式**：a) 上传图片发起；b) 指定已有植物发起（跳过识别或复用已识别品种）；c) 携带用户自选植物品种。
2. **识别置信度门槛**：识别置信度 < 0.6 → 不写入"已识别品种"，工作流改走"未知品种"路径（检索通用养护知识并标注）。
3. **生成链路**：严格按第 8 章固定链路执行，每一步骤结果可观测（记录 `trace`）。
4. **落库**：每次生成建议持久化至 `ai_advices`，含识别结果、检索文档 ID 列表、`is_fallback`、`confidence`、`trace`（JSON），保证可追溯与来源展示。
5. **建议结构**：输出固定 JSON 分节（见 8.5），前端按分节渲染；每条建议必须携带来源或 fallback 标注，**禁止出现无来源的"编造"内容**。
6. **反馈闭环**：用户点"有用/无用"回写 `feedback`，作为后续检索排序与提示词迭代样本。

#### 5.4.4 交互规则
- 上传图片即时预览；识别阶段显示步骤进度（识别中→检索中→生成中），增强链路透明度。
- 建议页顶部展示识别结果卡片（品种 + 置信度），下方为分节建议与"参考来源"折叠列表。
- 降级时顶部黄色警示条："未匹配到该品种专属知识，以下为通用养护建议"。
- 生成接口为长耗时操作（预计 3~10s），前端必须支持 loading/取消；后端建议异步任务或流式（SSE）返回，v1 采用同步 + 前端 loading，超时 30s 返回 504。

#### 5.4.5 异常场景
见 10.2.4：识别失败、无图上传、AI 服务超时/不可用（降级为纯知识检索输出并标注）、检索无命中（fallback）、Token 过期。

| FR-506 | 个人资料与账号设置入口 | P1 |

#### 5.5.3 业务逻辑
1. **打卡定义**：一次打卡 = `{plant_id, care_type(watering/fertilizing/pruning/repotting/pest_control/other), content, check_in_date, image?}`。
2. **日期规则**：`check_in_date` 默认当天；不允许选择未来日期（返回 400）；同一植物同一天同一 `care_type` 视为重复打卡 → 返回 409（防误触），允许不同 care_type 多次打卡。
3. **统计口径**：连续打卡天数 = 从今天（或昨天）向前追溯的最长连续"有打卡记录"的自然日数；统计范围为全部植物（本用户）。
4. **打卡联动**：打卡记录同时写入 `care_records`（供 P3 图表与 AI 工作流节点 4 消费），二者共享数据源、不冗余存储。
5. **撤销限制**：仅允许撤销当天的打卡（历史打卡不可撤销，保证图表与 AI 上下文一致性）；撤销后对应指标不受影响（指标独立）。

#### 5.5.4 交互规则
- 月历点击日期弹出"打卡"底部抽屉：选择植物、养护类型、备注。
- 已打卡日期角标显示打卡次数；连续天数以徽标展示在顶部。
- 撤销操作二次确认。

#### 5.5.5 异常场景
见 10.2.5：未来日期、重复打卡 409、非本人植物 403、撤销非当日记录 400。

## 6. 业务逻辑总览

### 6.1 核心业务对象与关系
```
User 1 ──< Plant 1 ──< CareRecord（打卡）
                   └──< PlantMetric（指标）
                   └──< AiAdvice（AI 建议，关联 KnowledgeDoc 引用）
User 1 ──< Checkin（日历打卡，与 CareRecord 同源）
```

### 6.2 关键状态与流转
- **植物状态**（派生）：`healthy / attention / abnormal`，由 5.3.3 规则引擎按近 7 天指标 + 打卡节律计算，每次写指标/打卡后异步重算。
- **AI 建议**：`pending(生成中) → success / failed(降级成功亦可 success+fallback) / timeout`。
- **会话**：`valid → expired → (refresh) → valid | blacklisted(注销)`。

### 6.3 核心业务规则清单
| 规则号 | 规则 | 违反后果 |

| BR-01 | 所有数据访问必须带当前用户 user_id 过滤 | 403 |

| BR-03 | 同植物同日同类打卡唯一 | 409 |
| BR-04 | 打卡日期不得为未来 | 400 |
| BR-05 | 指标值必须在合法区间 | 400 |
| BR-06 | AI 输出必须携带来源或 fallback 标注 | 内部校验失败即重试/标记 |

| BR-08 | 删除植物级联清理关联数据（事务） | 事务回滚 |

## 7. 用户权限模型

### 7.1 角色定义
| 角色 | 说明 | 初始分配 |
|---|---|---|
| `ROLE_USER` | 普通用户：管理本人数据、使用 AI 功能 | 注册即得 |
| `ROLE_ADMIN` | 管理员：知识库维护、用户管理、AI 审计（预留） | 系统内置/手动分配 |

v1 仅开放 `ROLE_USER`；`ROLE_ADMIN` 用于知识库后台与运营，接口预置权限校验（见 7.2）。

### 7.2 权限矩阵
| 资源/操作 | ROLE_USER | ROLE_ADMIN | 未登录 |
|---|---|---|---|
| 登录/注册/刷新 | ✔ | ✔ | ✔ |
| 本人 plants/metrics/checkins/ai_advices 读写 | ✔ | ✔ | ✘ |
| 他人数据读写 | ✘(403) | ✘(403，v1 不开放) | ✘ |
| 知识库检索（AI 内部） | 只读 | 只读+维护 | ✘ |
| 用户管理/审计 | ✘ | ✔ | ✘ |

### 7.3 数据隔离策略
1. **应用层隔离（必须）**：所有业务 SQL/ORM 查询强制附加 `user_id = current_user.id`；仅凭资源 ID 无法跨用户访问。
2. **接口层隔离（必须）**：中间件解析 JWT 得到 `user_id` 注入请求上下文；对他人资源的访问统一返回 `403`，不泄露资源存在性（404/403 语义见 9.3）。
3. **AI 上下文隔离**：工作流节点 4 仅拼接**当前用户当前植物**的打卡记录，禁止混入他人数据。
4. **AI 建议落库隔离**：`ai_advices.user_id` 与 `plant_id` 双重归属校验。

### 7.4 JWT 鉴权流程
```
客户端 ──POST /auth/login──► 服务端校验 → 签发 {access(2h), refresh(7d)}
客户端 ──请求业务接口(Bearer access)──► 鉴权中间件：
  解析 → 校验签名/过期/黑名单 → 注入 user_id
  过期 → 返回 code=401 → 前端用 refresh 换新 access（/auth/refresh）
  刷新失败 → 跳登录页
```
- Token 载荷：`{sub: user_id, role, exp, iat, jti}`；密钥环境变量管理，禁止硬编码。
- 密码哈希 bcrypt 成本因子 ≥12；刷新 Token 支持服务端黑名单（注销/改密后立即失效）。

## 8. AI-RAG 工作流逻辑

### 8.1 固定链路（强制顺序，LangChain 编排）
```
[节点1] 图像识别
  多模态 LLM 识别上传图片 → 输出候选品种 + 置信度
   │
[节点2] 植物名称提取/归一化
  候选品种 → 同义词/学名映射 → 标准化到知识库品种名
  置信度<0.6 → 标记 unknown，跳节点3b
   │
[节点3] RAG 知识库相似文档检索（RAGFlow）
  以标准化品种名 + 用户问题(如"多久浇水")构造检索 Query
  → top_k=5 相似文档；相似度阈值=0.45，低于阈值视为无命中
   │
[节点3b]（可选，无命中时）通用养护知识模板检索
  检索"通用养护"类目知识，命中或使用内置标准养护知识
   │
[节点4] 用户历史打卡记录拼接
  查询当前用户当前植物近 30 天打卡 + 近 7 天指标
  → 结构化摘要（浇水频率、异常指标、最近操作）
   │
[节点5] LLM 个性化生成
  注入 [系统提示词 + 检索上下文 + 打卡摘要 + 输出Schema约束]
  → 输出分节建议 JSON（带来源索引 / fallback 标注）
```
**路由决策：** `节点1+2 → 节点3(命中) → 节点4 → 节点5` 为完整链路；`节点3 无命中` 时经 `节点3b` 走降级路径，但**仍执行节点4、5**（结合用户数据输出通用知识版建议并标注）。

### 8.2 节点级说明
| 节点 | 输入 | 输出 | 失败/降级 |
|---|---|---|---|
| 1 图像识别 | 用户图片 | `[{species, confidence}]` | 识别失败→提示重新拍摄/上传 |
| 2 名称归一化 | 候选品种 | 标准化品种名 + `is_known` | 无法映射→`is_known=false` |
| 3 RAG 检索 | Query + 品种 | `[{doc_id, content, score}]` top5 | 无命中→节点3b |
| 3b 通用检索 | "通用养护" | 通用知识文档 | 均无→内置标准知识 |
| 4 打卡拼接 | user_id+plant_id | 结构化养护摘要 | 无记录→"新用户"提示 |
| 5 LLM 生成 | 上下文 | 分节建议 JSON | LLM 异常→返回可读错误 503 |

### 8.3 提示词设计（核心约束）
**系统提示词要点（务必实现）：**
1. 角色：专业植物养护专家，输出中文。
2. **强约束防幻觉**：只能依据「参考文档」与「用户打卡摘要」作答；参考文档未覆盖的内容必须输出该品种通用常识并**必须标注 `source_type=general`**；不得编造具体数值、农药名、未提供的引用。
3. 若用户打卡显示最近过度浇水等异常，必须优先引用打卡摘要给出纠正建议。
4. 输出结构严格遵循 8.5 Schema。
5. 禁用 Markdown 表格；每分节≤150字。

**用户侧输入注入：** 识别品种、用户问题（如"叶子发黄怎么办"）、打卡摘要、检索文档列表（含 doc_id 便于回引）。

### 8.4 防幻觉与降级策略（强制）
| 策略 | 实现 |
|---|---|
| 引用绑定 | 每条建议携带 `doc_ids`；无 doc 支撑的必须置 `source_type=general` |
| 阈值兜底 | 检索相似度 <0.45 → 不将弱命中文档注入上下文，直接降级 |
| 置信度兜底 | 识别 <0.6 → 未知品种路径 + 标注 |
| 降级标注 | `is_fallback=true`，前端明示"通用知识，非品种专属" |
| 输出校验 | 生成后 Schema 校验；缺失字段/未标注来源视为失败重试 1 次 |
| 可追溯 | 全链路 `trace` 落库（识别结果/检索 top5/摘要/提示词 hash） |

### 8.5 输出结构与来源标注
```json
{
  "species": "绿萝",
  "confidence": 0.92,
  "is_fallback": false,
  "summary": "一句话养护概览",
  "sections": [
    {
      "key": "watering",
      "title": "浇水",
      "content": "建议每周浇水1-2次……",
      "doc_ids": ["doc-001", "doc-002"],
      "source_type": "knowledge"          // knowledge | general
    }
  ],
  "warnings": ["检测到土壤湿度过高，存在烂根风险"]
}
```
- `source_type=general` 的分节前端必须显示"通用知识"角标。
- `doc_ids` 用于前端"参考来源"折叠列表（`GET /ai/advices/{id}` 附带文档标题/片段）。

### 8.6 质量指标（验收口径，见 11.4）
- RAG 命中率（`is_fallback=false` 占比）目标 ≥80%。
- 来源可追溯率：100% 建议携带 `doc_ids` 或 `source_type=general` 标注。
- 建议生成端到端耗时目标 ≤10s（P95）。
- 知识幻觉率（人工抽检）目标 ≤5%。

## 9. 前后端交互规则

### 9.1 接口设计规范
- 风格：RESTful，路径 `POST/GET /api/v1/<模块>/...`；统一前缀 `/api/v1`。
- 请求/响应：JSON（UTF-8）；图片上传 `multipart/form-data`。
- 时间：ISO8601（`2026-10-26T10:00:00+08:00`）；日期字段 `YYYY-MM-DD`。
- 幂等：删除类接口重复调用返回相同成功或 404；打卡接口用 `(user_id, plant_id, care_type, check_in_date)` 唯一约束防重。
- 命名：接口/字段用英文小驼峰；资源复数。

### 9.2 统一返回格式
见 3.4。补充约定：
- 分页结构：`data: { items: [], total: 100, page: 1, page_size: 10 }`。
- 列表接口统一分页；`data` 无数据返回 `{}` 或 `{items:[], total:0,...}`，禁止返回 null。

### 9.3 错误码约定
| code | 语义 | HTTP | 典型场景 |
|---|---|---|---|
| 200 | 成功 | 200 | — |
| 400 | 参数/业务校验失败 | 400 | 指标越界、未来日期 |
| 401 | 未认证/Token 失效 | 401 | 无 token、过期、黑名单 |
| 403 | 权限不足/越权访问 | 403 | 访问他人资源 |
| 404 | 资源不存在 | 404 | 植物/建议不存在 |
| 409 | 资源冲突 | 409 | 用户名重复、重复打卡 |
| 429 | 请求过频（限流） | 429 | AI 接口滥用 |
| 500 | 服务端内部错误 | 500 | 未捕获异常 |
| 503 | AI 服务不可用 | 503 | LLM/检索服务宕机 |
| 504 | AI 生成超时 | 504 | 链路 >30s |
| AI_FALLBACK | 业务标识：本次为降级输出 | 200 | `code=200` + `data.is_fallback=true`（前端用字段判断，不单设业务码） |

> 约定：`code` 使用上述字符串常量；业务异常以 `code` 为准，前端对 400/401/403/404/409/429 做统一 Toast 处理，401 走自动刷新链路。

### 9.4 鉴权
- Header：`Authorization: Bearer <access_token>`。
- 公开接口白名单：`POST /api/v1/auth/register|login|refresh`。
- 非白名单接口缺少/非法 token → 401；`ROLE_ADMIN` 专属接口校验角色，不满足 → 403。

### 9.5 分页/排序/筛选
- 分页：`page`(≥1)、`page_size`(1~50，默认10)。
- 筛选/排序通过 query 参数传递，服务端白名单校验字段名，防注入。

### 9.6 文件上传
- `POST /api/v1/upload/image`（鉴权）：`multipart` 字段 `file`。
- 校验：类型 jpg/png/webp，≤5MB；返回 `{url}`。
- 安全：服务端校验 MIME 与魔数，禁止脚本文件；文件名服务端生成，URL 不暴露物理路径。

| TC-501 正常打卡 | 已登录+植物 | 今日打卡浇水 | code=200，日历标记 |
| TC-502 重复打卡 | 今日已浇水 | 再次浇水打卡 | code=409 |
| TC-503 连续天数 | 连续 3 天有打卡 | 查 stats | 连续=3 |

### 11.2 接口单元测试（Skill：接口单元测试）
- 覆盖所有 `/api/v1` 接口：正常、参数非法、鉴权缺失、越权、分页边界（page=0、page_size=51）、错误码正确性。
- 依赖隔离：数据库用测试库；AI 链路用 mock（不真实调用 LLM/识别服务）以验证编排与降级分支。
- 覆盖率目标：后端核心模块行覆盖 ≥80%。

### 11.3 权限校验测试（Skill：权限校验测试）
- 未登录访问全部业务接口 → 401。
- 用户 A 对用户 B 的 plants/metrics/checkins/ai_advices 全部读写 → 403。
- 撤销他人打卡 / 删除他人植物 → 403。
- 越权路径不泄露资源存在性（404 与 403 语义正确）。
- AI 上下文不含他人数据（构造双用户打卡，断言生成上下文仅含本人）。

### 11.4 AI 质量验收（核心）
| 指标 | 目标 | 验收方式 |
|---|---|---|
| RAG 命中率 | ≥80% | 抽样 50 个真实品种图，统计 is_fallback=false 占比 |
| 来源可追溯率 | 100% | 断言每条分节含 doc_ids 或 source_type=general |
| 知识幻觉率 | ≤5% | 人工抽检 40 条建议 |
| 端到端耗时 | P95 ≤10s | 压测脚本 |
| 降级标注正确性 | 100% | fallback 建议均含前端可见标注 |

## 13. 数据模型设计（Tortoise-ORM 落地参考）

> 字段命名英文小驼峰；时间戳由 ORM 自动管理；`user_id/plant_id` 均建索引并参与隔离查询。

**users**
| 字段 | 类型 | 说明 |
|---|---|---|
| id | BIGINT PK | 主键 |
| username | VARCHAR(32) UNIQUE | 用户名 |
| email | VARCHAR(128) UNIQUE | 邮箱 |
| password_hash | VARCHAR(128) | bcrypt 哈希 |
| nickname | VARCHAR(32) | 昵称 |
| avatar_url | VARCHAR(512) | 头像 |
| role | VARCHAR(16) | ROLE_USER/ROLE_ADMIN |
| is_active | BOOL | 启用 |
| created_at/updated_at | DATETIME | 时间戳 |

**plants**
| 字段 | 类型 | 说明 |
|---|---|---|
| id | BIGINT PK | 主键 |
| user_id | BIGINT FK→users | 归属（隔离键） |
| name | VARCHAR(64) | 用户命名 |
| species | VARCHAR(64) NULL | 品种（AI 识别/手动） |
| image_url | VARCHAR(512) | 图片 |
| location | VARCHAR(64) | 摆放位置 |
| status | VARCHAR(16) | healthy/attention/abnormal（派生） |
| planted_at | DATE | 种植日期 |
| notes | TEXT | 备注 |
| created_at/updated_at | DATETIME | 时间戳 |

**care_records（打卡/养护记录，P5 同源）**
| 字段 | 类型 | 说明 |
|---|---|---|
| id | BIGINT PK | 主键 |
| user_id | BIGINT FK | 归属（冗余便于隔离查询） |
| plant_id | BIGINT FK→plants | 植物 |
| care_type | VARCHAR(24) | watering/fertilizing/pruning/repotting/pest_control/other |
| content | VARCHAR(512) | 备注 |
| image_url | VARCHAR(512) | 打卡图 |
| check_in_date | DATE | 打卡日 |

| 唯一约束 | (user_id, plant_id, care_type, check_in_date) | 防重复 |

**plant_metrics（指标）**
| 字段 | 类型 | 说明 |

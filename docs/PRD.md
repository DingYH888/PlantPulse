## 2. 项目概述

### 2.1 背景与目标
用户缺乏专业植物养护知识，容易因浇水过频、光照不足、施肥不当等原因导致植株死亡。本产品通过 **拍照识别植物 + RAG 知识库检索 + 用户历史打卡数据** 三重信息融合，生成**个性化、可追溯、防幻觉**的养护建议，帮助用户科学养植。

**核心目标：**
1. 建立每株植物的数字化档案与养护数据沉淀（植物记录 + 数据统计 + 日历打卡）。
2. 通过 AI-RAG 固定工作流输出「有知识库依据」的个性化养护建议。
3. 形成「识别 → 养护 → 记录 → 反馈 → 优化建议」的闭环。

### 2.2 产品定位
面向 C 端家庭园艺爱好者的**智能养植助手**：既是养护记录工具（工具属性），也是个性化养护顾问（AI 属性）。

### 2.3 目标用户与典型场景
| 用户画像 | 典型场景 |
|---|---|
| 新手养植者 | 买了绿萝不知道多久浇一次水 → 在 AI 养护页提问/上传照片 → 获得分节建议 → 打卡记录 |
| 进阶养植者 | 多盆植物需要差异化养护 → 按植物查看四维度统计与异常告警 |
| 出差/健忘用户 | 依赖日历打卡与连续打卡统计，保持养护连续性 |

### 2.4 术语与缩写
| 术语 | 说明 |
|---|---|
| RAG | Retrieval-Augmented Generation，检索增强生成 |
| ChromaDB | 本地持久化向量数据库，本项目**唯一的知识检索引擎** |
| LangChain | LLM 链式工作流编排框架（LCEL 管道） |
| MaaS | 阿里云百炼专属模型服务地址；与 dashscope 公共兼容地址可切换 |
| 打卡（记录） | 用户对某株植物的一次养护行为记录（浇水/施肥/修剪/换盆/病虫害防治/其他） |
| 会话（session） | AI 多轮对话的标识，同一 `session_id` 的追问共享上下文 |
| Fallback | 降级输出：知识库无匹配时输出的通用养护知识（需标注） |
| SSE | Server-Sent Events，服务端流式推送协议，本项目 AI 生成使用 |
| 长势健康分 | 按指标正常/待关注/异常折算的 100/60/20 分，用于统计图表 |

## 3. 总体架构

### 3.1 系统架构（逻辑视图）
```
┌──────────────────────────────────────────────────────────────┐
│                 前端 Vue 3 (Vite) + NaiveUI                   │
│  登录注册 │ 植物记录/打卡 │ 数据统计 │ AI 养护 │ 个人中心      │
└───────────────┬──────────────────────────────┬───────────────┘
                │ HTTPS / REST(JSON)            │ 图片上传(Multipart)
                │ AI 生成：SSE(fetch+Stream)    │ 静态资源：/static
                ▼                              ▼
┌──────────────────────────┐   ┌───────────────────────────────┐
│      FastAPI 后端网关     │   │  本地文件存储 static/uploads   │
│  JWT 鉴权 · 数据隔离 · 限流 │◄─►│  （uuid 文件名，经 /static 暴露）│
└───────┬──────────────────┘   └───────────────────────────────┘
        │
        ├─► 业务模块：auth / plants / metrics / stats / checkins / user / upload
        │
        ├─► AI 模块（LangChain LCEL 工作流）
        │    节点0 问题解析 → 节点1 图像识别 → 节点2 品种归一化
        │    → 节点2.5 植物定位 → 节点3/3b 知识检索(ChromaDB)
        │    → 节点4 打卡摘要 → 节点5 LLM 生成（同步 / 流式）
        │
        └─► 数据层：Tortoise-ORM → MySQL 8 / SQLite · ChromaDB(向量)
```

**设计理由：** 后端采用**单体分层 + 模块化路由**，契合 Vibe Coding 模块化开发与 Skill 质检；AI 链路独立为编排层，检索源、图像识别模型、LLM 均可通过配置替换；前端与后端完全分离，开发期由 Vite 代理 `/api` 与 `/static`。

### 3.2 技术栈

| 层 | 选型 | 版本 / 说明 |
|---|---|---|
| 前端框架 | Vue 3 + Vite | Vue `^3.5.0`，Vite `^5.4.0` |
| UI 组件库 | NaiveUI | `^2.45.3`，**全量引入**（`app.use(naive)`） |
| 状态/路由 | Pinia + Vue Router | `^2.2.0` / `^4.4.0`，HTML5 history |
| 图表 | ECharts | `^5.5.0`，按需注册 Line/Bar |
| HTTP | Axios + 原生 fetch | Axios 走 REST；fetch + ReadableStream 走 SSE |
| 后端框架 | Python 3.13 + FastAPI + Uvicorn | fastapi `>=0.115,<1.0` |
| ORM | Tortoise-ORM（异步） | `>=0.22.0` + `aiomysql` / `aiosqlite` |
| 数据库 | MySQL 8（生产/开发）/ SQLite（测试） | utf8mb4 |
| 鉴权 | PyJWT + bcrypt | HS256，单 Token 7 天，bcrypt cost 12 |
| 验证码 | captcha + Pillow | 4 位数字，落库 5 分钟一次性 |
| AI 编排 | LangChain（LCEL） | 锁定 `0.3.27` 稳定线，禁止 1.x |
| 向量库 | ChromaDB | `>=1.0.12,<2.0`，本地持久化 `backend/chroma_db` |
| LLM / Embedding | 阿里云百炼 OpenAI 兼容接口 | `qwen3.8-omni-flash` / `qwen3.7-text-embedding-flash` |
| 虚拟环境 | Windows `.venv` | 项目根唯一 `.venv`，Python 3.13.7 |

### 3.3 全局强制规范（来自 systemprompt，本文档全部需求遵守）
1. AI 模块 = LangChain 链式工作流 + 向量检索，优先检索知识库，再结合用户打卡记录生成个性化建议。
2. 所有模块开发完成后，必须适配内置 Skill：**代码自动质检、接口单元测试、权限校验测试**。
3. 全局 JWT 鉴权、用户数据隔离（任何跨用户数据访问一律 403）。
4. AI 固定工作流链路：问题解析 / 图像识别 → 植物名称提取 → 知识库相似文档检索 → 用户历史打卡记录拼接 → LLM 个性化生成（详见第 8 章）。
5. 代码单一职责、可复用、注释完整、无冗余；交付输出附带：代码路径、依赖、启动命令、单测用例。
6. 禁止幻觉：LLM 输出必须优先匹配知识库内容；无匹配则输出通用标准养护知识并**标注**（`is_fallback=true` + 前端明示"通用知识"）。

### 3.4 统一接口返回格式
所有业务接口（含错误）返回统一结构：
```json
{
  "code": "200",        // 业务码，字符串。见 9.3 错误码表
  "msg": "success",     // 人类可读消息（中文）
  "data": { }           // 业务数据；无数据时为空对象 {}
}
```
- HTTP 状态码与业务码独立：HTTP 仅表达传输/网关层语义，业务结果以 `code` 为准。
- `data` 为对象或数组容器，禁止裸返回标量；分页场景按 9.5 分页结构封装。
- **例外 1**：SSE 流式接口在建立流之后不再使用该结构，改用 `event: stage|delta|done|error` 协议（见 8.6）；建流前的错误仍返回标准结构与 HTTP 状态码。
- **例外 2**：静态资源 `/static/*` 与 FastAPI 默认 404/405（未匹配路由、方法不允许）当前不受统一格式覆盖，属已知缺口（见 15 章）。

### 3.6 运行与部署形态
- 前后端分离：前端 `5173`，后端 `8000`，开发期由 Vite 代理。
- 上传文件落本地磁盘（`backend/app/static/uploads`），由 FastAPI `StaticFiles` 挂载 `/static`；生产可替换为对象存储，接口返回 URL 不变。
- 应用为**单实例优先**设计：AI 限流与多轮会话记忆均为进程内状态，多 worker 部署时会话与限流不共享（见 15 章）。
- 时区：业务自然日统一按 `Asia/Shanghai` 计算；数据库时间戳由 ORM 自动写入。

## 5. 功能需求详情

> 每个页面统一结构：`5.x.1 页面说明 / 5.x.2 功能点与验收编号 / 5.x.3 业务逻辑 / 5.x.4 交互规则 / 5.x.5 异常场景`。

### 5.1 P1 登录注册

#### 5.1.1 页面说明
用户账号的注册、登录入口，单页双 Tab 切换「登录 / 注册」。未登录访问任何业务页面时统一重定向至本页。

#### 5.1.2 功能点（FR-1xx）
| 编号 | 功能点 | 优先级 | 状态 |
|---|---|---|---|
| FR-101 | 昵称 + 密码注册（含图形验证码） | P0 | ✅ |
| FR-102 | 昵称 + 密码登录 | P0 | ✅ |
| FR-103 | 登录态保持（单 JWT，7 天） | P0 | ✅ |
| FR-104 | 退出登录（前端丢弃 Token） | P1 | ✅ |
| FR-105 | 用户资料查看与修改（昵称/头像） | P1 | ✅ |
| FR-106 | 修改密码（校验原密码） | P1 | ✅ |
| FR-107 | 输入校验（昵称格式 / 密码强度 / 两次密码一致） | P0 | ✅ |
| FR-108 | 图形验证码生成与一次性校验 | P0 | ✅ |
| FR-109 | 头像上传（原子替换 + 旧图清理） | P1 | ✅ |

#### 5.1.3 业务逻辑
1. **注册**：`nickname` 3-20 位字母数字下划线且唯一；`password` 8-64 位且必须同时含字母与数字；`captcha_id` + `code`（4 位数字）校验通过且一次性消费。注册成功即签发 JWT 自动登录，返回 `msg="注册成功"`。
2. **验证码**：`GET /auth/captcha` 返回 `{captcha_id, image_base64}`；4 位数字明文仅落库（`captcha_codes.code`），不回传前端；有效期 5 分钟（`CAPTCHA_EXPIRE_MINUTES`），`is_used` 一次性；过期/已用/不匹配分别返回 400 中文提示。**登录不需要验证码**。
3. **登录**：`nickname` + `password`；bcrypt 校验（cost 12）。昵称不存在与密码错误统一返回 400「昵称或密码错误」，防账号枚举；`is_active=false` 返回 403「账号已被禁用」。
4. **会话**：单 Token 方案，`ACCESS_TOKEN_EXPIRE_DAYS=7`；载荷 `{sub, role, type:"access", jti, iat, exp}`；无 refresh token、无服务端黑名单。退出登录仅返回成功，Token 由前端删除（`jti` 为后续黑名单预留）。
5. **权限边界**：`/auth/captcha`、`/auth/register`、`/auth/login`、`/health` 为公开接口；其余全部要求 `Authorization: Bearer <token>`。

#### 5.1.4 交互规则
- 前端实时校验并给出中文内联提示：昵称 3-20 位字母数字下划线、密码 ≥8 位且含字母与数字、两次密码一致、验证码 4 位。
- 密码支持明文/密文切换；提交按钮 loading 态防重复提交。
- 注册失败（验证码错误等）自动刷新验证码，避免用户重复试错。
- Token 过期或非法时，首个接口返回 401 → 前端清理本地 Token 并硬跳转 `/login`（无自动刷新链路）。

#### 5.1.5 异常场景
| 场景 | code | 用户提示 |
|---|---|---|
| 昵称已存在 | 409 | 该昵称已被注册 |
| 验证码错误/过期/已使用 | 400 | 验证码错误 / 验证码已过期 / 验证码已使用 |
| 昵称或密码错误 | 400 | 昵称或密码错误 |
| 账号被禁用 | 403 | 账号已被禁用 |
| 未登录访问业务接口 | 401 | 未登录或凭证缺失，请先登录 |
| 原密码错误（改密） | 400 | 原密码错误 |

#### 5.2.3 业务逻辑
1. **数据隔离**：所有查询强制 `WHERE user_id = 当前登录用户`；对他人植物/打卡的读写一律 403，不存在返回 404。
2. **新增植物**：`name` 去空白后必填、≤64 字；`status` 由服务端固定为 `healthy`（当前无规则引擎派生）；`planted_at` 不允许未来日期。
3. **打卡内容**：`{plant_id, care_type, content?, record_date?, image_urls?}`；`care_type` 取 6 个枚举值；`record_date` 默认当天且禁止未来；同植物同类型同日**允许多条**（已移除早期唯一约束）。
4. **次数约定**：前端「次数」不新增数据库字段，而是拼接到 `content`（如 `备注；次数：2`），底层字段保持不变，仅调整界面语义。
5. **多图存储**：`image_urls` 数组序列化为 JSON 字符串写入 `plant_record.image_url`（单字段多图），读取时反序列化为 `images[]`。
6. **编辑打卡**：`PUT /checkins/{id}` 仅更新显式传入字段；`content`/`image_urls` 传 `null` 表示清空；未来日期 400。
7. **撤销打卡**：`DELETE /checkins/{id}` 仅允许撤销**当天**记录，历史记录返回 400；前端当前以「编辑」替代撤销入口，接口保留。

### 5.3 P3 数据统计

#### 5.3.1 页面说明
以图表可视化某株植物的养护数据：五维指标录入、按自然日聚合的趋势、四维度统计（长势/浇水/施肥/光照）与汇总卡片。数据源：手动录入指标 + 打卡记录。

#### 5.3.2 功能点（FR-3xx）
| 编号 | 功能点 | 优先级 | 状态 |
|---|---|---|---|
| FR-301 | 指标录入（温度/空气湿度/光照/土壤湿度/pH） | P0 | ✅ |
| FR-302 | 指标趋势折线图（按自然日聚合，7/30/90 天） | P0 | ✅ |
| FR-303 | 四维度统计（长势/浇水次数/施肥次数/平均光照） | P1 | ✅ |
| FR-304 | 指标异常高亮与告警提示 | P1 | ✅ |
| FR-305 | 导出数据（CSV） | P2 | ❌ |
| FR-306 | 统计汇总卡片（累计/平均/最高/最低/最新） | P1 | ✅ |
| FR-307 | 长势健康分（100/60/20 折算） | P1 | ✅ |

#### 5.3.3 业务逻辑
1. **录入校验**：温度 -20~60℃、空气湿度 0~100%、光照 0~200000 lux、土壤湿度 0~100%、pH 0~14；越界返回 400 中文区间提示；五项至少填一项；禁止未来日期。
2. **同日覆盖**：同植物同日再次录入时，服务端查当日最后一条并**整条覆盖**，不新增记录（`plant_metric` 无唯一约束，属接口层行为）。
3. **趋势聚合**：按自然日（东八区）取当日多条记录的平均值，返回连续日期序列，空日为 `null`；默认 30 天，支持 7/30/90 天。
4. **四维度统计口径**：
   | 维度 | 口径 |
   |---|---|
   | `growth` 长势 | 当日各指标按正常/待关注/异常折算 100/60/20，取均值；状态取最差项 |
   | `watering` 浇水 | 当日 `record_type=watering` 的打卡次数 |
   | `fertilizing` 施肥 | 当日 `record_type=fertilizing` 的打卡次数 |
   | `light` 光照 | 当日指标平均光照值（lux） |
5. **异常阈值（规则引擎，驱动 FR-304 与统计告警）**：
   | 指标 | 正常区间 | 待关注 | 异常 |
   |---|---|---|---|
   | 温度 | 15~30℃ | 8~15 或 30~35 | <8 或 >35 |
   | 空气湿度 | 40~70% | 30~40 或 70~80 | <30 或 >80 |
   | 土壤湿度 | 30~60% | 20~30 或 60~75 | <20 或 >75 |
   | 光照 | 5000~50000 lux | 2000~5000 | <2000 |
   | pH | 5.5~7.0 | 5.0~5.5 或 7.0~7.5 | <5.0 或 >7.5 |
   阈值为通用默认值，当前未实现「按品种覆盖阈值」。
6. **数据权限**：仅能查询本人植物；指标记录仅新增与同日覆盖，不支持删除单条（审计需要）。

#### 5.3.4 交互规则
- 图表基于 ECharts，长势用折线、其余用柱状；tooltip 展示原始指标与异常项。
- 空数据显示引导「暂无数据，请先录入指标」。
- 指标录入弹窗打开时按所选日期回填已有值，提交后刷新图表。
- 维度切换与时间范围切换均重新请求统计接口。

#### 5.3.5 异常场景
| 场景 | code | 用户提示 |
|---|---|---|
| 指标越界 | 400 | 温度需在 -20~60℃ 区间（其余同理） |
| 五项全空 | 400 | 请至少填写一项指标 |
| 未来日期 | 400 | 不能记录未来日期 |
| 非法 `days` / `dimension` | 400 | 参数校验失败 |
| 他人植物 | 403 | 无权访问该植物 |

### 5.4 P4 AI 智能养护（核心页面）

#### 5.4.1 页面说明
产品核心页：以**聊天会话**形式承载。用户输入问题或上传植物图片 → 走 AI-RAG 固定工作流（第 8 章）→ 通过 SSE 流式输出分节建议 → 完成后渲染识别结果、建议分节、风险提示、参考来源与反馈按钮。

#### 5.4.2 功能点（FR-4xx）
| 编号 | 功能点 | 优先级 | 状态 |
|---|---|---|---|
| FR-401 | 植物图像识别（返回品种 + 置信度） | P0 | ✅ |
| FR-402 | 生成个性化养护建议（触发完整 AI-RAG 链路） | P0 | ✅ |
| FR-403 | 建议分节渲染（概览/浇水/光照/施肥/温湿/病虫害/提示） | P0 | ✅ |
| FR-404 | 建议来源展示（引用的知识库文档 + 相似度） | P0 | ✅ |
| FR-405 | 降级标注（`is_fallback=true` 时提示"通用知识"） | P0 | ✅ |
| FR-406 | 历史建议与会话列表 | P1 | ✅ |
| FR-407 | 建议反馈（有用/无用/中性） | P2 | ✅ |
| FR-408 | 建议自动关联用户植物档案 | P1 | ✅ |
| FR-409 | SSE 流式输出（阶段进度 + 逐字正文） | P0 | ✅ |
| FR-410 | 停止生成（取消上游、不落库） | P0 | ✅ |
| FR-411 | 失败后重新发送 | P1 | ✅ |
| FR-412 | 会话管理（新建对话/打开历史/删除历史） | P1 | ✅ |
| FR-413 | 多轮上下文记忆（同一 session_id） | P1 | ✅ |

#### 5.4.3 业务逻辑
1. **触发方式**：a) 纯文本提问（后端节点 0 解析植物名）；b) 上传图片（节点 1 识别品种）；c) 图片 + 文本（以图像识别为准）。前端**不传** `plant_id` 与 `species`，`plant_id` 由后端节点 2.5 依据问题中的植物名/品种在本人档案中自动匹配。
2. **参数校验**：`image_url` 与 `question` 至少一项，否则 400「请输入养护问题或上传植物图片」；纯文本且解析不出植物名 → 400「请说明植物种类或名称」。
3. **识别置信度门槛**：视觉置信度 < 0.6 → 品种置为「未知品种」并标记 `low_confidence`，检索走通用知识路径。
4. **生成链路**：严格按第 8 章执行；同步接口返回完整结果，流式接口先推阶段进度再逐 token 输出。
5. **落库**：仅**成功完成**的建议落库至 `ai_advice`，含品种、置信度、`is_fallback`、分节内容、`doc_refs`、`trace`、`session_id`；失败/超时/用户停止均不落库。
6. **建议结构**：同步链路为固定 JSON 分节；流式链路为「【标记】正文」，服务端解析后转成同一结构化结果，前端最终渲染一致。
7. **反馈闭环**：用户点「有用/无用」写入 `feedback`（1/-1/0），可用于后续质量迭代。
8. **限流**：`identify`、`care-advice`、`care-advice/stream` 三个接口按用户 5 次/分钟（可配置），超限 429；历史查询不限流。
9. **超时**：链路整体受 `AI_TIMEOUT_SECONDS` 约束（代码默认 30s，`.env.example` 因 MaaS 生成较慢预置 120s），超时返回 504。

#### 5.4.4 交互规则
- **流式进度**：前置节点完成即推 `stage`（正在理解问题 / 识别品种 / 确认品种 / 匹配档案 / 检索知识库 / 读取打卡），节点 5 开始推 `delta` 正文。
- **正文渲染**：按「【标题】」实时分块渲染为绿色小节标题 + 正文，带闪烁光标；无正文时显示阶段文案 + 省略号。
- **停止生成**：发送按钮在生成中变为「停止」，点击 `AbortController.abort()`；保留已收到正文并标注"已停止生成"，不写入历史。
- **失败重试**：接口失败或中断时展示中文错误 + 已收到正文 + 「重新发送」按钮（不重复插入用户气泡）。
- **会话**：左侧（移动端为抽屉）展示历史会话列表（标题 / 轮数 / 更新时间）；「新对话」仅清空内存记忆不删数据库；删除会话同时删除数据库历史与内存记忆。
- **建议卡片**：顶部品种 + 置信度 + 「通用知识」角标；降级提示条；风险提示；分节正文带来源标签与 `doc_ids`；参考来源折叠区显示标题与相似度；底部反馈按钮（已反馈后禁用）。

#### 5.4.5 异常场景
| 场景 | code | 用户提示 |
|---|---|---|
| 未输入问题且未上传图片 | 400 | 请输入养护问题或上传植物图片 |
| 纯文本无法解析植物名 | 400 | 请说明植物种类或名称 |
| 图片不可访问 | 400 | 图片无法访问，请重新上传 |

## 6. 业务逻辑总览

### 6.1 核心业务对象与关系
```
User 1 ──< Plant 1 ──< PlantRecord（打卡，含多图 JSON）
                   ├──< PlantMetric（指标，同日覆盖）
                   └──< AiAdvice（AI 建议，按 session_id 分组）
User 1 ──< CaptchaCode（注册验证码，一次性）
User 1 ──< AiAdvice（归属隔离）
```
- 打卡统一使用 `plant_record` 单表，不再区分 `care_records` 与 `user_checkins`；日历打卡、统计、AI 打卡摘要均消费同一数据源。
- `ai_advice.session_id` 为会话分组键，空值历史数据以 `legacy-{id}` 兼容展示。

### 6.2 关键状态与流转
- **植物状态**：字段 `status` 默认 `healthy`；**当前无派生更新逻辑**（规则引擎未落地），前端展示不依赖该字段。
- **AI 建议**：`success`（唯一实际落库状态）；`pending/failed/timeout` 为模型枚举预留，失败链路在落库前返回，不会写入。
- **会话记忆**：进程内 `ConversationBufferMemory`，1 小时 TTL、最多 500 个会话、每会话保留最近 10 轮；重启失效。
- **登录态**：`valid → expired`（7 天）→ 重新登录；无 refresh 与黑名单。

### 6.3 核心业务规则清单
| 规则号 | 规则 | 违反后果 |
|---|---|---|
| BR-01 | 所有数据访问必须带当前用户 `user_id` 过滤 | 403 |
| BR-02 | 破坏性操作（改密/删会话/撤打卡）需校验身份与归属 | 403/401 |
| BR-03 | 同植物同日同类型打卡**允许重复**（唯一约束已移除） | — |
| BR-04 | 打卡/指标日期不得为未来 | 400 |
| BR-05 | 指标值必须在合法区间，且至少填一项 | 400 |
| BR-06 | AI 输出必须携带来源或 fallback 标注 | 服务端校验/改写，不通过则降级 |
| BR-07 | 识别置信度 <0.6 按未知品种路径处理 | 走通用知识 + 标注 |
| BR-08 | 删除用户/植物级联清理关联数据（ORM CASCADE） | 事务回滚 |
| BR-09 | 自然日统计统一按 `Asia/Shanghai` 切片 | 统计偏差 |
| BR-10 | 会话记忆按 `user_id:session_id` 隔离 | 串会话 |
| BR-11 | 注册验证码一次性、5 分钟有效 | 400 |
| BR-12 | 仅成功完成的 AI 建议落库 | 不产生半成品记录 |

| `ROLE_USER` | 普通用户：管理本人数据、使用 AI 功能 | 注册即得 |
| `ROLE_ADMIN` | 管理员：知识库维护、用户管理、AI 审计（预留） | 未开放 |

v1 仅使用 `ROLE_USER`；`role` 已签入 JWT，但当前无按角色限制的接口（`ROLE_ADMIN` 为后续扩展）。

### 7.2 权限矩阵
| 资源/操作 | ROLE_USER | ROLE_ADMIN | 未登录 |
|---|---|---|---|
| `/auth/captcha`、`/auth/register`、`/auth/login`、`/health` | ✔ | ✔ | ✔ |
| 本人 plants / metrics / stats / checkins / ai_advice 读写 | ✔ | ✔ | ✘ |
| 他人数据读写 | ✘(403) | ✘(403) | ✘ |
| 知识库检索（AI 内部） | 只读 | 只读 | ✘ |
| 用户管理/审计 | ✘ | 预留 | ✘ |

### 7.3 数据隔离策略
1. **应用层隔离（必须）**：所有 ORM 查询强制附加 `user_id = current_user.id`；仅凭资源 ID 无法跨用户访问。
2. **接口层隔离（必须）**：JWT 解析得到 `user_id` 注入请求上下文；他人资源统一返回 403，不存在返回 404。
3. **AI 上下文隔离**：节点 4 仅拼接当前用户当前植物的打卡与指标。
4. **AI 会话隔离**：会话列表/消息/删除均按 `user_id` 过滤，`session_id` 相同也不跨用户可见。
5. **静态资源**：上传文件为 uuid 文件名，URL 不含用户信息；当前未做图片访问鉴权（见 15 章）。

### 7.4 JWT 鉴权流程
```
客户端 ──POST /auth/login──► 校验昵称+密码 → 签发 access（7 天）
客户端 ──业务请求(Authorization: Bearer access)──► 依赖注入：
  解析 → 校验签名/过期/type=access → 加载 User → 校验 is_active
  失败 → 401 → 前端清理 Token → 跳转 /login
```
- Token 载荷：`{sub: user_id, role, type: "access", jti, iat, exp}`；密钥由 `JWT_SECRET` 环境变量管理。
- 密码哈希：bcrypt cost 12，仅存哈希；哈希与校验通过 `asyncio.to_thread` 执行，避免阻塞事件循环。
- 公开白名单：`/api/v1/health`、`/api/v1/auth/captcha|register|login`。

## 8. AI-RAG 工作流逻辑

### 8.1 固定链路（LangChain LCEL 编排）
```
[节点0] 问题解析
  纯文本提问 → LLM 抽取问题中出现的植物名（不臆测）
  有 image_url → 跳过，species_source=vision
  显式传 species → 跳过
  → 解析不出 → 400「请说明植物种类或名称」
   │
[节点1] 图像识别
  多模态 LLM 识别上传图片 → 候选品种 + 置信度（最多 3 个）
  无图 → 跳过
   │
[节点2] 植物名称提取/归一化
  别名表映射 → 标准品种名；视觉置信度<0.6 → 「未知品种」
  别名未命中 → 保留原名 + is_known=false
   │
[节点2.5] 植物定位
  未显式给 plant_id → 按「问题中出现的植物名 > 归一化品种一致」
  在本人档案中匹配，未命中为 None
   │
[节点3] 知识库相似文档检索（ChromaDB）
  品种可信 → Query 拼品种 + 过滤 {species} ∪ {category=general}
  品种不可信 → Query 拼「通用养护」+ category=general
  阈值过滤 → doc 粒度去重 → top_k
   │
[节点3b]（无命中时）通用养护知识回退
  再检索 category=general；仍无 → 注入通用知识上下文
   │
[节点4] 用户历史打卡记录拼接
  当前用户当前植物近 30 天打卡 + 近 7 天指标 → 结构化摘要
   │
[节点5] LLM 个性化生成
  同步：JSON 结构化输出（PydanticOutputParser）
  流式：astream 逐 token 输出「【标记】正文」
  → 服务端校验/绑定来源 → 结构化结果
```
**实际执行路径：**
- 纯文本：`0 → 2 → 2.5 → 3/3b → 4 → 5`
- 纯图片：`1 → 2 → 2.5 → 3/3b → 4 → 5`
- 图片 + 文本：`1 → 2 → 2.5 → 3/3b → 4 → 5`

**双通道：** `/ai/care-advice`（同步，兼容脚本与测试）与 `/ai/care-advice/stream`（SSE，前端实际使用）共用提示词组装与结果构建逻辑，避免口径漂移。

### 8.2 节点级说明
| 节点 | 输入 | 输出 | 失败/降级 |
|---|---|---|---|
| 0 问题解析 | question / user_species / image_url | `species`、`species_source` | 解析不出 → 400 |
| 1 图像识别 | image_url | `candidates[{species, confidence}]` | 图片不可访问 → 400；服务不可用 → 503；无候选 → 未知品种 |
| 2 名称归一化 | candidates / user_species | `species`、`confidence`、`is_known`、`normalize_source` | 未映射 → 保留原名 + `is_known=false` |
| 2.5 植物定位 | user_id / species / question | `plant_id` | 未命中 → None |
| 3 RAG 检索 | Query + 品种/类目 | `RetrievalResult{chunks, doc_refs, hit, error}` | 异常/无命中 → 节点3b |
| 3b 通用回退 | 「通用养护」+ 问题 | 通用知识文档或兜底上下文 | 均无 → 内置通用知识 |
| 4 打卡摘要 | user_id + plant_id | 结构化养护摘要 | 无记录 → 新用户上下文 |
| 5 LLM 生成 | 上下文 | 结构化建议 | 同步：重试 1 次后降级；流式：解析失败降级 `is_fallback=true` |

### 8.3 提示词设计（核心约束）
**视觉识别提示词：** 只根据图片判断；候选最多 3 个且按置信度降序；禁止虚高；无法可靠识别返回空数组；只输出 JSON。

**同步生成提示词要点：**
1. 只能依据「参考文档」与「用户养护摘要」作答；未覆盖内容只能给通用常识并标 `source_type=general`。
2. **禁止编造**具体数值、农药名称、文献引用、文档 ID。
3. `source_type=knowledge` 必须携带 `doc_ids`，且只能取自参考文档列表。
4. 参考文档为空/无关时全部标 general 且 `is_fallback=true`。
5. 打卡摘要出现过度浇水、烂根、暴晒等异常时，必须在 `warnings` 指出并优先给纠正建议。
6. 必须覆盖五个分节；每节 ≤150 字；禁用 Markdown 表格；严格 JSON。
7. 历史对话只用于连贯，不得作为本轮知识依据。

**流式生成提示词要点：** 不让模型输出 JSON，改为 7 个固定文本标记，必须独占行首、顺序不可调整、全部输出：
`【概览】【浇水】【光照】【施肥】【温度与湿度】【病虫害防治】【提示】`
正文禁止出现 `doc_id`/`source_type`/JSON 字段名；风险用中文分号分隔，无风险写「无」。

### 8.4 防幻觉与降级策略（强制）
| 策略 | 实现 |
|---|---|
| 引用绑定（同步） | 分节 `doc_ids` 必须是本轮真实检索文档，否则该分节降为 general |
| 引用绑定（流式） | 模型**不接触 doc_id**；服务端按分节主题关键词匹配本轮检索片段，最多绑定 2 个来源 |
| 阈值兜底 | 低于 `RAG_SCORE_THRESHOLD` 的切片不注入上下文 |
| 置信度兜底 | 识别 <0.6 → 未知品种路径 + 标注 |
| 降级标注 | `is_fallback=true`，前端显示「通用知识」角标与提示条 |
| 输出校验 | 分节 `key` 不得重复；knowledge 必带 doc_ids；缺失分节用内置通用知识补齐并标 general |
| 失败降级 | 节点 5 异常不返回 503，而是输出通用知识并标 `is_fallback=true`；仅图像识别服务不可用返回 503 |
| 可追溯 | `trace` 落库（各节点耗时、识别结果、检索结果、`prompt_hash` 等） |

### 8.5 输出结构与来源标注
**同步链路（内部结构化结果）：**
```json
{
  "species": "绿萝",
  "confidence": 0.92,
  "is_fallback": false,
  "summary": "一句话养护概览",
  "sections": [
    {
      "key": "watering",
      "title": "浇水",
      "content": "建议表土干燥后浇透……",
      "doc_ids": ["pothos-care-001"],
      "source_type": "knowledge"
    }
  ],
  "warnings": [],
  "doc_refs": [
    {
      "doc_id": "pothos-care-001",
      "title": "绿萝养护指南",
      "source": "species/绿萝.md",
      "score": 0.636,
      "category": "species"
    }
  ],
  "plant_id": 7,
  "status": "success",
  "trace": {}
}
```
- 五个分节固定 `key`：`watering / light / fertilizing / temperature_humidity / pest_control`。
- `doc_refs` 只保留被分节实际引用的文档，保证「来源列表 ↔ 分节 doc_ids」一一对应。
- 落库后详情额外包含 `id / session_id / question / plant_name / input_image_url / feedback / created_at`。

### 8.6 流式输出协议（SSE）
**接口：** `POST /api/v1/ai/care-advice/stream`，响应 `text/event-stream`，响应头含 `Cache-Control: no-cache`、`Connection: keep-alive`、`X-Accel-Buffering: no`。

**事件类型：**
| 事件 | data | 说明 |
|---|---|---|
| `stage` | `{"node": 0, "label": "正在理解你的问题"}` | 前置节点完成即推送进度 |
| `delta` | `{"text": "【概览】"}` | 节点 5 逐 token 正文增量 |
| `done` | `{"code":"200","msg":"success","data": 建议详情}` | 落库后的完整结果 |
| `error` | `{"code":"400","msg":"..."}` | 建流后发生的业务/系统错误 |
| `: ping` | 无事件体 | 每 10s 心跳注释帧，防止反代空闲断连 |

**协议示例：**
```text
event: stage
data: {"node": 0, "label": "正在理解你的问题"}

: ping

event: stage
data: {"node": 3, "label": "正在检索养护知识库"}

event: delta
data: {"text": "【概览】"}

event: delta
data: {"text": "绿萝整体状态良好，当前重点是控制浇水频率。\n【浇水】表土干燥 2~3 厘米后浇透。"}

event: done
data: {"code": "200", "msg": "success", "data": {"id": 128, "species": "绿萝", "is_fallback": false, "sections": [], "doc_refs": [], "trace": {}}}
```
- 建流前完成鉴权、限流、参数校验、植物归属校验，错误仍为标准 HTTP 状态 + 统一结构。
- 用户停止生成 = 取消上游任务，**不落库、不写记忆**。
- 心跳仅在节点 1~4 期间发送；节点 5 的 token 流本身是持续输出。

### 8.7 会话记忆与会话历史
| 项目 | 实现 |
|---|---|
| 存储 | 进程内字典，LangChain `ConversationBufferMemory` |
| 键 | `f"{user_id}:{session_id or 'default'}"` |
| 轮数 | 10 轮（`AI_MEMORY_MAX_TURNS`），保留最近 20 条消息 |
| TTL / 容量 | 1 小时；最多 500 个会话，超量淘汰最久未访问 |
| 持久化 | 仅内存，不写数据库/向量库，重启失效；多 worker 不共享 |
| 新对话 | `DELETE /ai/sessions/{id}` 只清内存记忆 |
| 删除历史 | `DELETE /ai/sessions/{id}/history` 删除数据库记录 + 内存记忆 |
| 历史兼容 | `session_id IS NULL` 的旧数据以 `legacy-{id}` 展示 |

### 8.8 知识库与检索参数
| 项目 | 值 |
|---|---|
| 文档目录 | `docs/knowledge_base/`（`species/` 60 篇 + `general/` 8 篇） |
| 支持格式 | `.md` / `.markdown` / `.txt` / `.pdf` / `.docx` |
| 入库跳过 | `README.md`、`_template.*`、隐藏文件 |
| 切片 | `RecursiveCharacterTextSplitter`，中文分隔符优先，600 字 / 重叠 100 |
| 向量库 | ChromaDB，集合 `plant_knowledge`，cosine，持久化 `backend/chroma_db` |
| Embedding | `qwen3.7-text-embedding-flash`（独立 Key） |
| 候选召回 | `max(top_k*3, 10)`，按 `doc_id` 去重后取 top_k |
| top_k | 代码默认 5；`.env.example` 预置实测调优值 3 |
| 阈值 | 代码默认 0.45；`.env.example` 预置实测调优值 0.55 |
| 通用文档占比 | 品种检索时通用文档最多保留 2 条 |
| 入库命令 | `python -m scripts.ingest_knowledge`（增量）/ `--rebuild`（全量） |

> 知识库文档编写规范见 `docs/knowledge_base/README.md`。

### 8.9 质量指标（验收口径，见 11.4）
- RAG 命中率（`is_fallback=false` 占比）目标 ≥80%。
- 来源可追溯率：100%（每条 knowledge 分节必须有 `doc_ids`，general 分节必须有标注）。
- 首字节时间（首个 `stage`）≤2s；完整生成 P95 ≤60s（实测 40~60s），上限受 `AI_TIMEOUT_SECONDS` 约束。
- 知识幻觉率（人工抽检）目标 ≤5%。
- 流式完整性：`delta` 累积正文与 `done` 结构化结果语义一致率 100%。

## 9. 前后端交互规则

### 9.1 接口设计规范
- 风格：RESTful，统一前缀 `/api/v1/<模块>`。
- 请求/响应：JSON（UTF-8）；图片上传 `multipart/form-data`；AI 流式为 `text/event-stream`。
- 时间：ISO8601（`2026-10-29T10:00:00+08:00`）；日期字段 `YYYY-MM-DD`。
- 幂等：删除类接口重复调用返回成功；打卡允许多条（无唯一约束）。
- 命名：接口路径与查询参数用 snake_case，响应字段用 snake_case，前端变量 camelCase、组件 PascalCase。

### 9.2 统一返回格式
见 3.4。补充约定：
- 分页结构：`data: { items: [], total: 100, page: 1, page_size: 10 }`。
- 列表接口统一分页；`data` 无数据返回 `{}` 或 `{items:[], total:0,...}`，禁止返回 `null`。

### 9.3 错误码约定
| code | 语义 | HTTP | 典型场景 |
|---|---|---|---|
| 200 | 成功 | 200 | — |
| 400 | 参数/业务校验失败 | 400 | 指标越界、未来日期、验证码错误 |
| 401 | 未认证/Token 失效 | 401 | 无 Token、过期、类型错误 |
| 403 | 权限不足/越权访问 | 403 | 访问他人资源、账号禁用 |
| 404 | 资源不存在 | 404 | 植物/建议/会话不存在 |
| 409 | 资源冲突 | 409 | 昵称重复 |
| 429 | 请求过频（限流） | 429 | AI 接口滥用 |
| 500 | 服务端内部错误 | 500 | 未捕获异常 |
| 503 | AI 服务不可用 | 503 | 依赖缺失、识别服务不可用 |
| 504 | AI 生成超时 | 504 | 链路超时 |

> 约定：`code` 均为字符串；业务异常以 `code` 为准；前端对 400/401/403/404/409/429 做统一 Toast，401 直接清理 Token 跳登录。

### 9.4 鉴权
- Header：`Authorization: Bearer <access_token>`。
- 公开接口白名单：`GET /health`、`GET /auth/captcha`、`POST /auth/register`、`POST /auth/login`。
- 非白名单接口缺少/非法 Token → 401；当前无角色鉴权依赖。

### 9.5 分页/排序/筛选
- 分页：`page`(≥1)、`page_size`(1~50，默认 10；会话列表默认 20)。
- 排序固定：植物按创建时间倒序；打卡按 `record_date` 倒序 + `id` 倒序；AI 建议按 `id` 倒序。
- 筛选通过 query 参数传递，服务端白名单校验枚举与区间，非法返回 400。

### 9.6 文件上传
- `POST /api/v1/upload/image`（登录）：`multipart` 字段 `file`。
- 校验：类型 `image/jpeg`、`image/png`、`image/webp`，≤5MB；服务端生成 uuid 文件名。
- 返回 `{url: "/static/uploads/<uuid>.<ext>"}`；前端通过 `/static` 代理访问。
- 头像使用 `PUT /api/v1/auth/avatar`（登录，原子上传 + 落库 + 清理旧图）。

## 10. 异常场景

### 10.1 全局异常

## 15. 已知限制与待办

> 本章用于记录「文档与代码仍存在的已知偏差」，避免验收时误判。均为当前实现的客观现状，不代表产品终态。

### 15.1 功能缺口
1. 植物仅支持新增与列表，**编辑/删除/图片更换未实现**；`/plants/:id` 为占位页且无入口。
2. `plants.status` 无派生逻辑，始终为 `healthy`。
3. 数据导出 CSV（FR-305）未实现。
4. 前端无 ESLint / 单元测试 / E2E，质量门禁仅 `npm run build`。
5. 未实现按品种覆盖指标阈值；阈值均为通用默认值。
6. `species_aliases.py` 仅覆盖 11 个标准品种、26 条别名，知识库中其余品种会被判为 `is_known=false`（虽仍保留原名参与检索，但降级判断会偏保守）；补齐 60 个品种中文名与拉丁学名是待办。
7. 知识库 frontmatter 的 `aliases` 字段当前仅作为元数据入库，未参与品种归一化（归一化只读内置别名表）。

### 15.2 工程与部署限制
1. AI 限流与多轮记忆为**进程内状态**，多 worker（`--workers > 1`）下会话可能串号、限流不共享；生产建议接 Redis 或固定单 worker。
2. 上传文件存本地磁盘，未做图片访问鉴权；生产建议对象存储 + 签名 URL。
3. 统一返回格式未覆盖未匹配路由（404）与方法不允许（405），当前返回 FastAPI 默认 `{"detail": ...}`。
4. `backend/sql/schema.sql` 末尾存在无条件 `DROP INDEX` / `ADD INDEX` 语句，新建库首次执行会因索引不存在报错中断；且外键未声明 `ON DELETE CASCADE`，与 ORM 的 CASCADE 行为不一致。生产建库后建议以 ORM/Aerich 迁移为准。
5. `scripts/smoke_tortoise.py` 仍按 5 张表与「重复打卡唯一约束」断言，与当前 6 表、约束已移除的实现不一致，运行会失败。
6. tzdata 已加入依赖（Windows `zoneinfo` 必需），缺失会导致 Tortoise 写库报 `ZoneInfoNotFoundError`。

1. 2026-10-29 已将根 `README.md`、`backend/README.md`、`frontend/README.md`、`docs/knowledge_base/README.md` 与本 PRD 一并按实现对齐，五份文档可作为交付与验收依据。
